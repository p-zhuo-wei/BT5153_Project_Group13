# Resume-Job Matching

A two-stage retrieve-and-rerank pipeline for matching resumes to job postings. The full workflow lives in `overall.ipynb`, which orchestrates code from `src/` and `eval/` and produces every metric, figure, and comparison table in `results/`.

## What the project does

Given a job posting and a pool of resumes, the system ranks stronger candidates nearer the top so recruiters review promising candidates earlier. The pipeline has two stages:

- **Stage 1 — first-stage retrieval** ranks the entire candidate pool per query.
  - **TF-IDF** lexical baseline (sparse cosine similarity)
  - **SBERT** dense bi-encoder (`all-MiniLM-L6-v2`)
  - **SPLADE** learned sparse retrieval (`naver/splade-v3`)
  - **FAISS** over SBERT embeddings (retrieval-only sanity check, not in the 3×3 grid)
- **Stage 2 — second-stage reranking** re-scores stage-1's shortlist:
  - **Cross-encoder** (`cross-encoder/ms-marco-MiniLM-L-6-v2`) — reranks top-50, returns top-10
  - **LLM** (`Qwen2.5-3B-Instruct` via LM Studio) — reranks top-20, returns top-10

This produces a 3×3 grid of `{TF-IDF, SBERT, SPLADE} × {none, CE, LLM}` plus a separate FAISS row for retrieval comparison. The project compares these on ranking quality (P@10, MRR, MAP, nDCG@10), runtime cost, and ranking-stability fairness under demographic perturbations.

## Reproduction steps

### 1. Set up the Python environment

```bash
# Recommended: conda env with Python 3.11 or 3.12
conda create -n bt5153 python=3.12
conda activate bt5153
pip install -r requirements.txt
```

### 2. Download the raw data

Place the two Kaggle CSVs at the expected paths:

```text
data/raw/Resume/Resume.csv             # from snehaanbhawa's Resume Dataset
data/raw/fake_job_postings.csv         # from shivamb's Real-or-Fake Job Postings
```

Both files are gitignored. Reviewers must download them manually from the links above.

### 3. Start LM Studio (required for stage-2 LLM cells)

1. Install [LM Studio](https://lmstudio.ai/)
2. Load the model **`Qwen2.5-3B-Instruct (Q4_K_M)`** — about 1.9 GB. Search "qwen2.5-3b-instruct" inside LM Studio and pick the Q4_K_M variant.
3. Start the local server (default base URL `http://localhost:1234/v1`).
4. Verify with the diagnostic cell at the top of `checking.ipynb` (returns valid JSON output, `reasoning_tokens: 0`).

If LM Studio is unreachable, all LLM cells will fall back to `load_saved_llm_outputs` and load the cached results in `results/metrics/grid_*+llm_*.csv` — preserving the rest of the notebook's behaviour.

### 4. Run the notebook

Open `overall.ipynb` and run cells top-to-bottom. The orchestrator is **cache-aware** — every cell skips its expensive work if its metric CSVs already exist on disk.

```bash
jupyter lab
# then open overall.ipynb
```

Run order matches notebook section numbering:

| Section | What runs | Cold runtime (M-series Mac) |
|---------|-----------|------------------------------|
| 0 | Imports, helpers, GRID_RESULTS registry | seconds |
| 1 | Build dataset, load test split, sanity-check matched-100 subset | ~1 min (cold) |
| 2 | TF-IDF pipeline: stage 1 + CE + LLM (subset) | ~1.5 hr (LLM dominates) |
| 3 | SBERT pipeline: stage 1 + CE + LLM (subset) | ~1.5 hr |
| 4 | SPLADE pipeline: stage 1 + CE + LLM (subset) | ~1.7 hr |
| 5 | FAISS pipeline (stage 1 only) | seconds |
| 6 | 3×3 grid summary table + bar plot | seconds |
| 7 | Fairness audit (TF-IDF + SBERT + SPLADE, validation split) | ~1 min |
| 8 | Runtime breakdown (stage 1, stage 1+2 pipelines) | seconds |

A full cold run on an M1 (8 GB) Mac with the LLM cells active takes roughly **5-6 hours**, dominated by the three LLM rerank cells (~50 min each). Warm reruns load from cached CSVs and complete in seconds.

### 5. Evaluation scope

- **Stage-1 retrievers** are evaluated on the full held-out test split (823 unique jobs, 197 candidate resumes per job).
- **Stage-2 rerankers (CE, LLM)** are evaluated on a **stratified random sample of 100 jobs** (`RANDOM_SEED=42`, stratified by `job_category` so the 100 jobs preserve the full-test category distribution within ±5%). The same 100 jobs are used for both CE and LLM, enabling paired bootstrap significance tests in Section 6's downstream tables.
- All comparisons report metrics at top-10.

## Labels — methodological note

No publicly available, human-annotated English-language resume-job matching benchmark exists at scale. The project constructs a weakly supervised benchmark using category and skill overlap:

- **Label 2** — same category, strong lexical and skill overlap (highly relevant)
- **Label 1** — adjacent category, partial overlap (relevant)
- **Label 0** — distant category, low overlap (not relevant)

For evaluation, `precision@k` / `recall@k` / `MRR` / `MAP` treat both 1 and 2 as relevant (binary `positive_threshold=1`). `nDCG@k` uses the graded `2^rel - 1` gain so highly-relevant items contribute more.

When a model surfaces a `(job, resume)` pair with no label in `data/splits/test.csv`, it is treated as relevance 0. Reported metrics are therefore conservative lower bounds — models that surface novel-but-genuinely-relevant candidates get penalised.

## Key results

Stage-1 retrievers (full held-out test, 823 queries):

| Model | P@10 | MRR | nDCG@10 | MAP |
|-------|------|-----|---------|-----|
| TF-IDF | 0.039 | 0.141 | 0.132 | 0.108 |
| SBERT | 0.029 | 0.110 | 0.100 | 0.083 |
| SPLADE | 0.044 | 0.155 | 0.158 | 0.124 |
| FAISS (SBERT vectors) | 0.029 | 0.098 | 0.100 | 0.067 |

Stage-1 + Stage-2 pipelines (matched 100-query subset):

| Pipeline | P@10 | MRR | nDCG@10 |
|----------|------|-----|---------|
| TF-IDF → CE | 0.048 | 0.169 | 0.159 |
| TF-IDF → LLM | 0.037 | 0.145 | 0.124 |
| SBERT → CE | 0.034 | 0.120 | 0.111 |
| SBERT → LLM | 0.032 | 0.163 | 0.128 |
| SPLADE → CE | 0.045 | 0.141 | 0.143 |
| SPLADE → LLM | 0.043 | 0.170 | 0.157 |

Headline finding: **TF-IDF remains the strongest cheap baseline**, SPLADE is the strongest stage-1 retriever, and rerankers improve some position-weighted metrics (MRR, nDCG) without dramatically lifting P@10.

## Caveats

- Relevance labels are heuristic proxies, not recruiter judgements. The full-test results should be read as a comparative benchmark under weak supervision rather than a hiring-quality estimate.
- Stage-2 rerankers are evaluated on the matched 100-query stratified subset due to LLM compute cost on a single laptop. The subset preserves full-test category distribution within ±5%.
- The LLM was originally configured with `gemma-4-e2b`. That model is reasoning-native and consumed all output tokens on chain-of-thought, leaving no content — every response fell through to the lexical fallback parser. The project switched to `qwen2.5-3b-instruct` (non-reasoning) which produces parseable JSON directly. Cached LLM artifacts in this repository are from the Qwen run.
- The fairness audit covers TF-IDF, SBERT, and SPLADE (val split with 7 demographic perturbations). LLM and CE fairness are not audited — adding them is left for future work.
- The proposal targets (P@10 ≥ 0.80, MRR ≥ 0.70) were not met. The conservative recommendation is to keep TF-IDF as the production default and treat rerankers as optional augmentations under operational-cost constraints.
